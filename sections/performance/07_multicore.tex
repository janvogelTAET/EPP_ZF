\section{Multicore \& Synchronisation}
\label{sec:multicore}

\begin{formel}[Amdahl für Kerne]
\[S(N)=\frac{1}{(1-p)+\dfrac{p}{N}}\]
$p=80\,\%$ parallel, $N=2$:
$S=\frac{1}{0.2+0.4}=1.67$. Dieselbe Formel wie für SIMD-Lanes
(Abschnitt~\ref{form:amdahl}) -- nur heisst $s$ jetzt $N$.
\end{formel}

\SW{Gründe für mehrere Kerne}
\begin{itemize}
\item Komplexität von HW nach SW verschieben: mehrere kleine schnelle
      RISC-Kerne statt eines grossen superskalaren Out-of-Order-Kerns
      -- aber \emph{zuerst} die Caches vergrössern, falls das Optimum
      noch nicht erreicht ist
\item Lizenzkosten steigen typisch \emph{nicht} linear mit der Kernzahl
\item little-big-Architekturen sparen Strom (z.\,B.\ 2 Effizienz- $+$
      2 Performance-Kerne)
\end{itemize}
\SW{HW-Grenze} RAM-Bandbreite. \SW{Nachteil} Datenkohärenz.

\subsection{Multitasking-OS (FreeRTOS)}
Pro Prozessor läuft genau \emph{ein} Task. Bei jedem System-Tick (z.\,B.\
20\,ms Timer-IRQ) kann der Scheduler nach Priorität wechseln -- technisch
nur durch Austausch des \T{Stackpointers}; jeder Task hat seinen eigenen
Stack. Neue Tasks aus der \emph{ready}-Liste; wartende wandern in die
\emph{blocked}-Liste.
\SW{Vorteil} keine Cycles für Polling, einfache Programmierung.
\SW{Problem} Datenkohärenz und geteilte Ressourcen.

\begin{falle}[Reentranz ist Pflicht]
Nicht reentrant: \R{temp} als \emph{globale} Variable in \R{swap()} --
zwei gleichzeitig aktive Instanzen zerstören sich gegenseitig.
Reentrant: \R{temp} \emph{lokal} (auf dem eigenen Stack) -- dann dürfen
Tasks und Kerne denselben Code teilen.
\end{falle}

\subsection{Sechs Ursachen für Kohärenzprobleme}
\label{sec:kohaerenz}
\begin{ztab}{@{}lX@{}}
Stale Data & Core 1 liest den alten Wert aus seinem Cache \\
Write-Write & beide schreiben gleichzeitig, Ergebnis unbestimmt \\
Read-Modify-Write & beide lesen 10, schreiben 11 -- ein Inkrement weg \\
Non-Atomic Multiword & 64\,Bit als zwei 32-Bit-Writes, Leser sieht Mix \\
Out-of-Order & \R{flag=1} wird vor \R{data=42} sichtbar \\
DMA vs.\ CPU & DMA liest, während die CPU noch schreibt \\
\end{ztab}

\begin{bsp}[Race Condition: \R{counter++}]
\begin{lstlisting}
counter++  ->  LOAD counter / ADD 1 / STORE counter

Core0: LOAD 42      Core1: LOAD 42
       ADD 1               ADD 1
       STORE 43            STORE 43   -> 43 statt 44
\end{lstlisting}
Je $10^6$ Inkremente ergeben \emph{nicht} $2\cdot10^6$.
Lösung: \R{lock(); counter++; unlock();} bzw.\ konzeptionell
\R{atomic\_fetch\_add(\&counter,1)}.
\end{bsp}

\subsection{Kooperation paralleler Prozesse}
\SW{Mutual Exclusion brutal} Scheduler, andere CPUs und Interrupts
abschalten und Caches flushen. \SW{Sauber} Semaphore/Mutex.
\begin{ztab}{@{}lX@{}}
Kommunikation & \T{Mailbox} (blockiert) $|$ \T{Message Queue} \\
Synchronisation & \T{Semaphore} (zählend, z.\,B.\ 3 gleiche Ressourcen)
  $|$ \T{Mutex} $|$ \T{Flags} \\
\end{ztab}

\begin{falle}[Priority Inversion]
Ein niederpriorer Task hält das Semaphor und blockiert damit einen
hochprioren; ein mittelpriorer verdrängt den niederprioren dauernd
\ra der hochpriore wartet indirekt auf einen Task, der nie drankommt.\\
\T{Lösung:} \T{Mutex} mit \emph{Priority Inheritance} -- der Halter erbt
vorübergehend die hohe Priorität.\\
\emph{Mars Pathfinder 1997}: genau dieser Fehler, sporadische Resets;
Fix war Priority Inheritance in VxWorks.
\end{falle}

\SW{SMP} identische CPUs, \emph{ein} OS.
\SW{AMP} eine OS-Instanz pro Kern, braucht HW-Unterstützung für
Semaphore/Mutex.

\subsection{RP2350 Multiprozessor-Subsystem}
$2\times$Armv8-M (DSP, FPU, Security) \emph{oder} $2\times$\R{RV32IMAC};
Mischbetrieb über \R{ARCHSEL} möglich, braucht aber zwei Programmimages.
\begin{itemize}
\item symmetrische Bussicht: beide Kerne erreichen alle Ressourcen gleich
      schnell
\item pro Kern zwei 32-Bit-Links zum Systembus (Instruktion $+$
      Load/Store $=$ Harvard)
\item ungenutzte Kerne in Reset mit abgeschaltetem Takt
      \ra \emph{null} dynamische Leistung (CMOS)
\item alle Interrupts gehen an beide Kerne, der interne Controller abonniert
\end{itemize}

\SW{SIO (Single-cycle IO)}
\begin{ztab}{@{}lX@{}}
Spinlocks & 32 Stück, Ein-Bit-Flag je Adresse. \emph{Lesen} $=$ Anspruch
  (Rückgabe $\neq0$ \ra erhalten), \emph{Schreiben} (beliebiger Wert) $=$
  freigeben. Bei Gleichstand gewinnt Core\,0. Nur für sehr kurze
  kritische Abschnitte (Spinning ist teuer). \\
FIFOs & Inter-Processor Mailboxes, 32\,Bit breit, 4 Einträge tief;
  Flags \R{VLD}/\R{RDY}/\R{ROE}/\R{WOF} (letzte zwei sticky); IRQ\,25 \\
Doorbells & 8 Flags je Richtung, ein IRQ pro Kern (26), für
  \emph{kumulative, ungeordnete} Ereignisse \\
Rest & \R{CPUID} (0/1), Integer-Divider, Interpolator,
  RISC-V-Platform-Timer, GPIO fürs Bitbanging; alles doppelt für
  secure/non-secure \\
\end{ztab}

\begin{formel}[Global Exclusive Monitor (empfohlen statt Spinlocks)]
Processing Elements: Core\,0, Core\,1 und \emph{der DMA}.
Reservation Page $=$ beliebige 16-B-ausgerichtete SRAM-Region.
Ein exclusive Write gelingt nur, wenn
(a)~ein exclusive Read desselben PE voranging,
(b)~nur eine Reservation offen ist,
(c)~Adresse, Grösse und Rechte übereinstimmen und
(d)~kein anderes PE seither in dieselbe Granule geschrieben hat.
Sonst wird der Write verworfen und meldet das zurück.
\end{formel}
\begin{lstlisting}
arm_acquire:               lr.w rd,(rs1)
  LDREX   r1,[r0]            ; Reservation setzen
  CMP     r1,#0            sc.w rd,rs2,(rs1)
  STREXEQ r1,r2,[r0]         ; rd=0 ok, !=0 fehlgeschlagen
  CMPEQ   r1,#0
  BNE     acquire
\end{lstlisting}
RISC-V zusätzlich \R{amoadd/amoswap/amoand/\dots} (Extension \R{A}).

\subsection{Reentranz}
\label{sec:reentranz}
\begin{formel}[Die Regel]
Eine Funktion ist \T{reentrant}, wenn zwei Instanzen gleichzeitig aktiv
sein dürfen -- also wenn sie keinen Zustand ausserhalb ihres eigenen
Stackframes anfasst. Nur reentranter Code darf von Tasks \emph{und} von
mehreren Kernen geteilt werden.
\end{formel}
\begin{lstlisting}
int temp;                   | void swap(int *x,int *y) {
void swap(int *x, int *y) { |   int temp;      /* lokal! */
  temp = *x;                |   temp = *x;
  *x = *y;                  |   *x = *y;
  *y = temp;                |   *y = temp;
}  /* NICHT reentrant */    | }  /* reentrant */
\end{lstlisting}
Der einzige Unterschied ist, wo \R{temp} steht. Weitere Killer:
\R{static}-Variablen, globale Puffer, nicht-reentrante
Bibliotheksfunktionen (klassisch \R{strtok}, \R{printf} ohne
Locking), und Hardware-Register, die als Zustand benutzt werden.

\subsection{Mutual Exclusion: die Werkzeuge}
\label{rez:mutex}
\begin{ztab}{@{}lX@{}}
\multicolumn{2}{@{}l}{\textbf{Kommunikation}}\\
Mailbox & \emph{blockiert} -- ein Platz, Schreiber wartet, bis gelesen
  wurde \\
Message Queue & gepuffert, mehrere Nachrichten, Reihenfolge bleibt \\
\addlinespace
\multicolumn{2}{@{}l}{\textbf{Synchronisation}}\\
Semaphor & Zähler („Bahnsignal“). \T{Counting Semaphore} verwaltet
  mehrere gleichartige Ressourcen -- drei Restaurant-Toiletten: Zähler
  3, jeder \R{Take} dekrementiert \\
Mutex & \T{Mutual Exclusion}: binär \emph{und} mit Besitzer. Nur wer
  genommen hat, darf zurückgeben \\
Flags & Signalisierung ohne Datenübergabe \\
\end{ztab}
FreeRTOS kennt drei Semaphortypen: \T{binär}, \T{counting} und
\T{Mutex}.

\begin{falle}[Prioritätsinversion -- und warum Mutex $\ne$ Semaphor]
Ein Task \emph{niedriger} Priorität hält ein Semaphor. Ein Task
\emph{hoher} Priorität will es und blockiert. Jetzt verdrängt ein Task
\emph{mittlerer} Priorität den niedrigen -- und damit indirekt auch den
hohen. Der wichtigste Task wartet auf den unwichtigsten.\\[2pt]
\T{Lösung} Der \T{Mutex} kennt seinen Besitzer und kann ihm deshalb
vorübergehend die Priorität des Wartenden geben
(\emph{priority inheritance}). Ein reiner Semaphor kann das nicht -- er
weiss nicht, wer ihn hält.\\[2pt]
\merkzeile Prominentestes Opfer: \T{Mars Pathfinder} 1997 -- der
Watchdog setzte den Rover wiederholt zurück, weil genau diese Inversion
auftrat.
\end{falle}

\begin{lstlisting}
SemaphoreHandle_t mutex;
mutex = xSemaphoreCreateMutex();        /* vor dem Scheduler */
/* im Task: */
xSemaphoreTake(mutex, portMAX_DELAY);   /* ... oder Timeout */
  /* kritischer Abschnitt */
xSemaphoreGive(mutex);
\end{lstlisting}

\SW{Die brutalen Alternativen} Scheduler anhalten, andere CPUs anhalten,
Interrupts sperren, Caches flushen. Funktioniert, zerstört aber die
Echtzeitfähigkeit -- und im Mehrkernfall reicht das Sperren der eigenen
Interrupts ohnehin nicht.
\begin{falle}[Einkern-Lösungen tragen nicht über Kerne]
Auf einem Kern genügt es, Interrupts zu sperren oder den Scheduler
anzuhalten -- das Betriebssystem ist dann nur einmal aktiv. Bei
\emph{mehreren} Kernen läuft der andere Kern weiter. Semaphore und
Mutex über Kernegrenzen brauchen deshalb \T{Hardware-Unterstützung}:
den globalen Exclusive Monitor (\R{LDREX}/\R{STREX} bei ARM,
\R{lr.w}/\R{sc.w} bei RISC-V) oder dedizierte Spinlocks.
\end{falle}

\subsection{SMP und AMP}
\label{rez:smpamp}
\begin{ztab}{@{}lX@{}}
\T{SMP} & Symmetric Multiprocessing: \emph{ein} Betriebssystem verteilt
  Tasks auf alle Kerne. Die Kerne sind gleichwertig, jeder Task kann
  überall laufen \\
\T{AMP} & Asymmetric: jeder Kern hat sein \emph{eigenes} Programm bzw.\
  OS, Kommunikation über FIFOs/Shared Memory. Beim RP2350 nötig, wenn
  ein Kern ARM und der andere RISC-V ist (zwei Images) \\
\end{ztab}

\begin{bsp}[FreeRTOS SMP auf dem RP2350]
Zwei Kerne, ein FreeRTOS:
\begin{lstlisting}
configNUM_CORES              2  /* beide Kerne nutzen */
configRUN_MULTIPLE_PRIORITIES 0 /* nur gleiche Prio gleichzeitig */
configUSE_CORE_AFFINITY      1  /* vTaskCoreAffinity... aktiv */
configUSE_PREEMPTION         1
\end{lstlisting}
\begin{lstlisting}
xTaskCreate(vTaskSMP, "A", taskSize, NULL, 1, &handleA);
xTaskCreate(vTaskSMP, "B", taskSize, NULL, 1, &handleB);
xTaskCreate(vTaskSMP, "C", taskSize, NULL, 1, NULL);
xTaskCreate(vTaskSMP, "D", taskSize, NULL, 1, NULL);
vTaskCoreAffinitySet(handleA, (1 << 0));  /* A nur auf Core 0 */
vTaskCoreAffinitySet(handleB, (1 << 1));  /* B nur auf Core 1 */
vTaskStartScheduler();
\end{lstlisting}
\R{A} und \R{B} sind festgenagelt, \R{C} und \R{D} wandern. Im Task
fragt man die eigene Lage ab mit \R{get\_core\_num()},
\R{xTaskGetCurrentTaskHandle()} und \R{vTaskCoreAffinityGet()}.
\end{bsp}
\begin{falle}[\R{configRUN\_MULTIPLE\_PRIORITIES}]
Steht es auf \T{0}, laufen \emph{nur Tasks gleicher Priorität}
gleichzeitig auf beiden Kernen. Das verhindert, dass ein
niederpriorer Task parallel zu einem hochprioren läuft und ihm
Busbandbreite und Cache wegnimmt -- kostet aber Parallelität. Steht es
auf 1, wird mehr parallel ausgeführt, die Prioritätssemantik ist aber
nicht mehr die von einem Kern gewohnte.
\end{falle}
\begin{falle}[\R{printf} ist nicht reentrant]
Zwei Kerne, die gleichzeitig \R{puts} aufrufen, produzieren
verschränkten Buchstabensalat. Darum in jedem SMP-Beispiel ein
Wrapper:
\begin{lstlisting}
void vSafePrint(char *out) {
  xSemaphoreTake(mutex, portMAX_DELAY);
  puts(out);
  xSemaphoreGive(mutex);
}
\end{lstlisting}
Das ist die praktische Anwendung von \ref{sec:reentranz} und
\ref{rez:mutex} in drei Zeilen.
\end{falle}
